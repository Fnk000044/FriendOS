1. Demo 故事线闭环
   ─────────────────────────────────────────
   确保以下流程一气呵成，不卡顿、不报错：

   首次启动 → 隐私同意 → 仪表盘概览 → 写日记（触发情绪分析）
   → 查看情绪页面（热力图+趋势图）→ AI 聊天（上下文感知）
   → 聊天中出现危机词 → 危机干预弹窗（5秒倒计时+热线）
   → 风险仪表盘（综合评分+雷达图）

   检查项：
   [ ] seedDemoData 构造完整的 7 天故事线数据
   [ ] 每个页面切换无白屏/报错
   [ ] 危机弹窗触发正常（测试关键词："不想活了"）
   [ ] 风险评分 >0 且雷达图有数据

2. 消除"答辩尴尬点"
   ─────────────────────────────────────────
   以下功能如果被评委问到会暴露问题，建议处理：

   (a) 方言检测（ChineseLocalizationService.dialectMap）
       问题：18 条数据，未接入任何功能
       处理：从 ChineseLocalizationService 中删除 dialectMap 相关代码
             或在 UI 中隐藏入口

   (b) 网络俚语词典（ChineseLocalizationService.slangDict）
       问题：27 条，远不够覆盖中文网络用语
       处理：合并核心词条到 SentimentService 关键词表，删除独立模块

   (c) 打字行为分析（TypingBehavior）
       问题：数据量不足，无法证明有效性
       处理：保留采集（展示技术前瞻性），但不要在演示中重点展示
             如果评委问到，话术："这是探索性功能，需要更多数据验证"

   (d) StubProvider 模板回复
       问题：回复质量低，暴露系统弱点
       处理：改为明确提示"请配置 AI 模型"，不要给假回复

   (e) 情绪预测数值
       问题：线性回归预测 7 天情绪，准确性存疑
       处理：UI 改为"趋势方向"展示（上升/下降/稳定），
             去掉具体数值预测，避免评委追问准确率

3. 风险评估统一
   ─────────────────────────────────────────
   当前三处都在算风险等级，算法和权重不一致：
   - RiskScoringEngine.cjs（后端）
   - RiskAssessment.ts（前端服务）
   - EmotionAnalysisEngine.cjs（后端）

   处理：统一使用 RiskScoringEngine 作为唯一入口，
         其他两处改为调用它或只做子维度计算。
         答辩时说"统一的风险评分引擎"比"三个模块各算一遍"更有说服力。

4. 危机检测多级确认
   ─────────────────────────────────────────
   当前问题：23 个关键词直接触发弹窗，误报率高
   评委可能问："你怎么区分'不想活了'和'不想活了这种无聊的课'？"

   方案：3 级确认
   Level 1：关键词命中 → 内部标记"疑似"（不弹窗）
   Level 2：ONNX BERT 负性概率 >70% → 升级为"可能"
   Level 3：LLM 结合上下文判断（当日日记+最近对话）→ 确认才弹窗

   同时添加排除规则：
   - 引号内容（歌词/台词引用）
   - 成语/俗语（"九死一生"、"生不如死"）
   - 明显的非自杀语境（"无聊到想死"、"困死了"）

   答辩话术："我们采用三层过滤机制，关键词预筛 + 情感模型确认
            + LLM 语义判断，最大程度减少误报"

5. 个人基线对比
   ─────────────────────────────────────────
   当前：BehaviorAnalyzer 已有基线计算，但展示不够直观

   优化：在风险仪表盘中增加"与你的基线对比"区块
   - "你最近 7 天的平均心情是 3.8，低于你的基线 4.2"
   - "你的任务完成率从 80% 下降到 45%"
   - 用箭头和颜色直观展示偏离程度

   答辩话术："系统会建立每个人的个人基线，检测偏离而非绝对值，
            避免了'一刀切'的阈值问题"

6. 否定词处理
   ─────────────────────────────────────────
   SentimentService 当前注释写着"intentionally loose, no negation detection"
   如果被问到会很被动。

   最简实现：否定词窗口检测
   否定词列表：不、没、别、勿、未、莫、非、无
   规则：关键词前 3 个 token 内出现否定词 → 反转情感极性
   示例："想死" → 危机  |  "不想死在这种无聊的课上" → 非危机

   ─────────────────────────────────────────
   "数据不出本机"是核心卖点，准备以下答辩要点：
   - 所有数据存储在本地 IndexedDB，不上传任何服务器

   - API 密钥使用 Electron safeStorage 加密（系统级加密）
   - 同步功能仅在局域网内进行，使用 UUID 令牌认证

================================================================================
答辩准备 — 高频问题与回答
================================================================================

Q: "你们的情感分析准确率是多少？"
A: "我们采用三层分析架构：关键词预筛（覆盖率高）+ ONNX BERT 模型
   （准确率约 85%）+ LLM 语义判断（处理歧义场景）。三层互补，
   兼顾召回率和准确率。同时系统会建立个人基线，检测偏离而非绝对值。"

Q: "怎么区分真实的自杀意念和隐喻？"
A: "我们有三层过滤：关键词命中后，ONNX 模型判断情感极性，
   最后由 LLM 结合对话上下文和日记内容做语义判断。
   同时有排除规则过滤成语、歌词、网络用语等误报场景。"

Q: "0.6B 的模型能做好分析吗？"
A: "0.6B 模型负责最后的语义判断层，处理的是已经被关键词和 BERT
   预筛过的高置信度文本。对于简单的情感分类和危机判断，
   0.6B 参数量足够。更重要的是我们的分层架构，
   不是所有分析都依赖 LLM。"

Q: "数据安全怎么保障？"
A: "三个层面：数据存储在本地 IndexedDB，不上传服务器；
   API 密钥使用系统级加密（Windows DPAPI）；
   同步功能仅在局域网内，使用 UUID 令牌+10分钟 TTL。"

Q: "跟市面上的产品有什么区别？"
A: "三个核心差异：一是本地推理，数据不出本机，解决隐私顾虑；
   二是无感识别，通过行为模式（日记频率、任务完成、写作模式）
   而非问卷被动检测；三是中国文化适配，
   包括蓄意表达检测和学期压力感知。"
